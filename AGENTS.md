# Agent instructions

This file is the working contract for coding agents and other automated contributors to Vita3K. Follow the repository's existing conventions first; use this file to find the right scope, feedback loop, and validation command quickly.

## Project map

Vita3K is a C++23 PlayStation Vita emulator. The root `CMakeLists.txt` owns the build and `CMakePresets.json` contains the supported platform/toolchain presets.

| Area | Location | Start here when the task concerns |
| --- | --- | --- |
| Emulator libraries | `vita3k/<component>/` | Runtime behavior, HLE services, memory, CPU, I/O, graphics, audio, or input |
| Main executable | `vita3k/` | Application startup, platform integration, or top-level target wiring |
| HLE modules | `vita3k/modules/` | Sce* module exports and Vita API behavior |
| Desktop UI | `vita3k/gui-qt/` | Qt windows, settings, dialogs, and desktop resources |
| Tests | `vita3k/mem/tests/`, `vita3k/module/tests/` | Allocator and module argument-layout behavior |
| Build and packaging | `CMakeLists.txt`, `CMakePresets.json`, `cmake/`, `.ci/` | Toolchains, dependencies, CI, packaging, and generated build files |
| Developer tools | `tools/` | Module generation, localization generation, and native utilities |
| Android frontend | `android/` and `vita3k/android/` | Gradle, JNI, Android packaging, or Android-specific behavior |
| Translations | `i18n/`, `vita3k/lang/` | Qt translations or runtime language catalogs |
| Vendored dependencies | `external/` | Third-party code or git submodule revisions |

Avoid broad searches and edits under `external/` unless the task explicitly targets a dependency. Most changes should stay within one component and its tests.

## First pass

Before editing:

1. Run `git status --short` and preserve unrelated changes.
2. Read the nearest `CMakeLists.txt` and the relevant headers/tests before changing implementation code.
3. Confirm submodules are present with `git submodule status --recursive`; initialize them with `git submodule update --init --recursive` when needed.
4. Search for existing call sites and tests with `rg` before introducing a new helper, option, or convention.

Do not use destructive cleanup (`git reset --hard`, `git checkout --`, or recursive deletion) to solve a build problem. Build directories are disposable; source changes and submodule state are not.

## Fast feedback loop

The read-only repository preflight is:

```sh
./check.sh
```

It checks whitespace errors, validates that CMake can read the preset file, and verifies clang-format without modifying files. It requires `git`, `cmake`, and `clang-format`. Run an individual check when an environment is intentionally minimal:

```sh
./check.sh --diff-only
./check.sh --format-only
./check.sh --cmake-only
```

To apply formatting, use `./format.sh` (or `format.bat` on Windows). Use `./format.sh --check` for a formatter-only read-only check.

## Build and test loop

Use a CMake preset rather than hand-maintained compiler flags. On macOS or Linux, a typical local loop is:

```sh
cmake --preset linux-ninja-clang
cmake --build build/linux-ninja-clang --config Debug --parallel
ctest --test-dir build/linux-ninja-clang --build-config Debug --output-on-failure
```

Choose the platform-appropriate preset from `cmake --list-presets`. The CI presets in `CMakePresets.json` are useful when reproducing CI, but they expect CI dependency setup. The full CI-equivalent desktop path is:

```sh
bash ./.ci/build-desktop.sh --preset <preset> --config Release
```

For a focused iteration after a build exists:

```sh
cmake --build build/<preset> --config Debug --target mem-tests module-tests --parallel
ctest --test-dir build/<preset> --build-config Debug --output-on-failure -R '^(mem|module)$'
```

The two registered CTest names are `mem` and `module`. If dependencies are missing, report the exact configure or build command and the first actionable error; do not silently weaken compiler or linker settings.

Android uses the Gradle project under `android/`; follow `.ci/build-android.sh` for the CI artifact path. Do not mix Android-generated assets into a desktop-only change.

## Change rules

- Match the surrounding C++ style and `.clang-format`; keep public headers and implementation details separated as the component already does.
- Add or update a focused test when behavior can be exercised without launching the emulator.
- Keep generated output out of source directories. Runtime language catalog files are generated by `tools/i18n/generate_lang_catalog.py`; Qt `.qm` files and `gitver.h` are generated in the build tree.
- Treat `external/` as vendored code. Prefer changing Vita3K integration code; update a submodule only when the task explicitly requires it and record the reason.
- Preserve platform guards (`ANDROID`, `WIN32`, `APPLE`, and Linux feature detection) when editing shared code.
- Do not change dependency versions, CI permissions, packaging behavior, or release metadata as incidental cleanup.
- Keep diffs narrow. Do not reformat unrelated files or rewrite generated/vendor content.

## Completion report

Before handing off, inspect `git diff --stat` and `git diff --check`. Report:

- what changed and why;
- tests/checks run and their results;
- anything not run because a dependency or platform was unavailable; and
- any generated files or follow-up work that remains.
